# 设计演化记录：为何改目标

> **历史因果记录，不是对路线的投票或未来的命令。** 未来模型可推翻这些想法；应尽量留下推翻的依据。

| 探索阶段 | 解决的问题 | 观察到的不足 | 对下一阶段的启发 |
| --- | --- | --- | --- |
| 暮灯星栈 | 静态文明倾向测试、视觉卡片、手机访问 | 主要是访谈和规则评分，不是开放叙事 | 保留作为独立既有应用 |
| 明清人物镜 12/28 题 | 四维历史人物近似、开放回答、云端语义分析 | “历史问题”仍是试题，缺乏奇遇、欲望、代价与英雄旅程 | 让故事发生在测量之前，拟合放在结局 |
| 甲申异闻录固定七幕 | 宝物、门客、成就、资源、戏剧化事件、叙事 UI | 分支和手牌演示可用，但仍靠三选一和预写事件，玩家自行规划无法改变世界 | 让 GM 创造事件与规则，Harness 管状态 |
| 酒馆开源系统调研 | 认识角色卡、世界书、背景/立绘、会话管理 | 完整酒馆框架可能带来与目标无关的部署和 UI 包袱 | 参考能力而不是盲目整体移植 |
| Pi 式最小 Agent | 通用提示词、按需技能、工具和世界存档 | 仅靠提示词无法可靠保证持久化、多人隔离与账本一致性 | Agent 创造与提议，Harness 记录与安全承接 |
| 地区 × 阶层丛书 | 不必遍历故事分支；地图提供薄设定、权力结构和示例 | 静态等级不足以表达异地贬级、乔装、借势越级 | 以地区/当地接触阶层选卷，叠加实时身份关系 |
| 当前阶段 | 完成接手文档、验证最简 GM Harness 是否成立 | 新目标尚未有运行中实现，旧原型不能当作完成品 | 保留旧原型并以实验验证新的抽象 |

### 两个不同的“简化”

1. **减少预先写死的剧情**：让 AI 用世界约束与实时事实形成事件，地图不要求全量剧情树。
2. **不把现实条件藏起来**：状态持久化、权限、防滥用、上下文窗口、可验证成就和素材带宽仍需要 Harness 负责；简化不等于取消这些问题。

### 四个标签帮助未来 Agent 自由思考

- `FACT`：现在能复验的事实/实现/部署状态；说明检验办法和时间。
- `HYPOTHESIS`：关于生成式故事、身份视角与用户体验的推断；欢迎提出反例。
- `EXAMPLE`：奇物、地图、卡牌、故事字数、模型、技术栈或数值，仅供激发新思路。
- `OPEN`：尚无证据的设计选择和未解风险。

任何先前的“必须七幕”“12 张卡”“先上 Pi SDK”“单图转 GIF”等固定做法都应视为**有上下文的旧策略**，而不是新的系统法则。

### 当前最值得守住的抽象

未来可以任意更换实现，只要服务的仍是：让游客自主做事且世界连续；给 Agent 足够空间即兴创造与长期记忆；网页作为通用 Harness 不依赖特定剧本；加入世界/地图/插画不要求重写引擎；公开使用不暴露用户数据或账户密钥。

如果某种更简单的结构确实能实现这些目的，应欢迎替换本记录中任何策略。
